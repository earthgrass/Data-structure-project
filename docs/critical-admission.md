# 特急插单预检与冲突让位

本轮授权新增规划接纳策略，基线 `be3e523`。普通与紧急订单、旧API调用继续沿用原流程；Dashboard手动新增特急订单发送 `protect_critical: true`，进入原子预检。三级优先级与所有签收、容量硬约束不变。

## 规则

1. 副本校验订单身份、Decimal需求和窗口；暂停副本的后继动作，完成已进入的装货、道路行驶、卸货、服务。真实时钟、位置和载货不推进，等待动作可立即结束。
2. 使用原主目标、原两级规划器与独立验证器，首先尝试保留全部既有承诺。
3. 若失败，允许副本中仍在仓库、未进入装货动作的普通/紧急承诺重新竞争。既有特急、车上货物与中转站货物不撤回。新特急按原优先级/截止时间/ID确定性规则参与接纳。
4. 只有新特急具有按时签收、合法容量和返仓的完整验证方案才提交输入变更。被让位订单保留唯一ID与货物位置，回到pending，不取消、不伪装送达；下一步续程重新接纳可行订单。新特急成为受保护任务。
5. 真实已进入动作继续完成，到检查点再次规划并独立验证。通过后等待用户播放；不会跳过在途动作。后续新的路况和订单事件仍可能改变可行性，预检不是对未来交通的永久保证。
6. 无可验证方案返回422 `critical_unavailable`，携带真实失败候选report和中文提示。API不提交副本，原计划、revision、事件、订单和运行状态完全保留，失败ID可以修改窗口后重新提交。

## 界面与接口

新增特急时自动开启预检；失败提示留在弹窗，保留表单内容并聚焦错误，建议调整截止时间。容量、封路问题同时提示，避免暗示延长时间必然能解决。成功提示列出退回待规划的订单ID，已有路线变化、影响摘要与时间轴继续展示实际结果。

`add`可选布尔字段`protect_critical`只适用于critical订单；省略字段保留历史接口行为。成功响应附加`critical_admission`，包含订单ID、预检检查点时间、输入版本、预测签收及受影响订单ID；历史事件保存同一记录。该响应只是预检证据，预测签收不写为实际签收。

手动新增之外的批量自动生成及已有订单优先级修改仍使用历史接口；本轮不隐式扩大其语义。

## 实现与边界

`dispatch/admission.py`协调副本、两次既有规划和提交，不另写路径或排序算法。时间为O(副本大小 + K次检查点推进 + 2次原规划)，空间为O(会话副本 + 计划)。API仍在锁内操作命令副本；前端不自行推测可行性。逐车容量全程Decimal。

“未找到按时方案”是当前启发式与单路径闭包的结论，不是穷举不可行证明。不自动放宽低优先级订单截止时间，不保证最少撤回订单；撤回后仍无可验证特急方案则整笔回滚。

## 回归

新增8项unittest：容量冲突让位、极短截止原子拒绝、既有特急保护、已进入装货保护、无冲突保持承诺、精确签收边界冲突及真实执行、在途副本不推进真车、实际HTTP拒绝后同ID重试。原849项Python测试及325项前端断言保留。最终全量记录见 `experiments/critical-admission-regression.json`。

实际全量857项通过，失败0、错误0、退出码0；unittest 275.019秒，外部单调计时277.405495秒。前端325项断言及TypeScript/Vite构建通过（83模块）。额外运行cost容量冲突实例，特急接纳、普通单因容量退回，独立验证通过。修改源码禁用依赖/排序扫描及diff检查通过，未修改任何原测试文件。
