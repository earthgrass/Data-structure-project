# 规划解释：影响摘要、拒单证据与订单时间轴

本轮只实现用户批准的三项功能：重规划影响摘要、无法接单的原因解释、订单时间窗时间轴。原有两级配送、手写Dijkstra与插入选择、逐车Decimal容量、签收完成截止、三级优先级和独立验证继续适用；不增加新的求解器，不把解释模块当作可行性证明。

## 界面入口

- **路线变化**：显示新计划相对于旧计划剩余行程的距离、模拟成本、行驶时间及逐车差额；展开共同订单的预计签收提前／延后，并列出新接纳、不再规划、取消／过期和未接纳的ID。
- **订单与新增订单结果**：展开“为什么未接纳”，查看真实候选中的车辆、站点、阻塞任务与具体容量、时间或路径证据。
- **时间窗**：每张独立订单都有一条窗口区间，分别标注预计到达、服务开始、预计签收和实际签收；可搜索订单／地点／车辆，筛选待完成任务及低余量任务。原有严格／宽松初始实验对照继续保留。

沿用UI-UX-Pro-Max已有物流工作台设计，不再向地图增加常驻大浮层。针对时间轴的技能搜索未得到可直接适用的区间图匹配，本轮采用通用可访问性原则和手写SVG区间图：文字、形状、线型与颜色共同区分数据，并提供可直接阅读的数值。没有把趋势折线或置信带建议强套到订单窗口，也没有引入现成图表或算法包。

时间轴提醒阈值是展示过滤条件，默认5分钟且可调整；它不改变后端时间窗、容量、路线或订单状态。预计余量为 `deadline - expected.signoff`，0是合法的精确边界，不能用真假值判断把0显示为缺失。未规划订单没有可计算的计划余量。

## 后端数据契约

现有会话API仍返回完整快照。本轮以新增字段方式扩展快照，`schema_version`及历史接口继续兼容：

```text
planning_insights
  impact: Impact | null
  timeline: { now, plan_revision, stale, stale_reason, orders: TimelineOrder[] }
  explanations: { source, revision, traffic_version, stale, items: OrderExplanation[] }
```

`Plan.to_dict()`同样新增 `explanations`；原有 `accepted`、`deferred`、路线、指标、输入指纹和验证报告不变。失败代码继续用于兼容；自然语言与结构化证据是附加解释。没有新增写入命令，前端也不在展示层推算另一份调度结果。

### 影响摘要

`Impact`包含：

| 字段 | 口径 |
|---|---|
| `at` | 成功应用新计划的真实模拟检查点时刻 |
| `baseline_revision` / `plan_revision` | 旧／新规划输入修订号；不是两个HTTP响应的修订号 |
| `baseline_traffic_version` / `traffic_version` | 两份计划各自使用的路况版本 |
| `comparison_basis` | 固定为 `remaining_at_checkpoint` |
| `historical_baseline` | 固定为true；旧计划只作为历史反事实对照 |
| `objective_before` / `objective_after` | 两次规划目标，不能假定一定相同 |
| `before` / `after` / `delta` | `distance`、`cost`、`travel_time`，差额为新减旧 |
| `vehicles` | 每车同样三组指标及 `changed` 标记；动作或时刻改变也属于变化 |
| `orders` | 每ID的旧／新预计签收分钟、差额及 `earlier`／`later`／`unchanged`／`newly_planned`／`removed` |
| `newly_accepted` | 新计划具有配送服务、旧剩余计划没有的ID |
| `no_longer_planned` | 原剩余计划具有配送服务、新计划没有的ID |
| `cancelled` | 自上次应用计划后新取消／过期的ID，包括此前未接纳订单；历史取消不重复计数 |
| `deferred` | 新计划明确未接纳的ID |

首次计划没有旧基线，`impact=null`，不能伪造“从0到本计划”的优化差额。后续成功应用计划前，先从旧计划删除**已经存在完成事件的完整Action身份**：车辆、动作类型、起终点、开始／结束、清单、批次、路况及指标均参与身份比较。并行车辆可能在相同时间结束不同动作，因此不能用 `action.end <= now` 代替完成证据。

前后两份剩余路线在同一检查点比较。距离、成本与行驶时间直接累计真实路线Action数据，包含尚未执行的出仓、途中、返仓道路；不拿旧全程指标与新剩余指标相减。成本沿用模拟道路成本模型，行驶时间不冒充包含等待、装卸和服务的总任务时长。

影响摘要应用后冻结，普通动画和真实执行推进不会让该摘要不断变化；下一次成功应用计划才替换。订单或路况再次改变、尚未形成可用计划时，界面明确标为“上次已应用计划的影响”。

新旧服务集合可能不同，例如多送一张订单或取消一张订单。此时距离／成本增减只是业务变化的代价，不能单独宣称质量改善。提前／延后只对前后均有预计服务的同一订单比较；新接纳或不再规划的订单不生成虚构时间差。分类列表允许交叉，例如已取消订单也可能属于“不再规划”，不能把这些列表简单相加当作互斥总量。

交通变化后旧路线没有重新验证，甚至可能经过新封闭道路。`historical_baseline`明确其比较用途，不表示旧路线当前仍可执行。独立验证约束新计划安全应用；解释摘要不代替该验证。

### 订单时间轴

每个 `TimelineOrder`包含 `order_id`、`destination`、`priority`、`status`、`earliest`、`deadline`、`expected`、`actual`和 `deferred_reason`。同址多单保留不同ID和不同服务时刻，不能以地点数量代替订单数量。

`expected`／`actual`的共同结构为：

```text
{ vehicle, arrival: number | null, service_start, signoff, slack }
```

- `arrival`是车辆本次连续停留该地点的到达时刻。由逐条行驶动作及原始车辆位置得到，在等待和同址连续服务期间保持不变；不是把服务开始时间改名为到达时间。缺少可定位证据时返回null。
- `service_start`是该订单的服务开始；`signoff`是该订单的服务完成。最早时间限制前者，截止时间限制后者。
- `slack`为该订单截止减签收完成时刻，严格按原时间模型计算。
- `expected`来自已应用计划的配送动作，代表预计结果；没有当前计划、已取消／过期／签收、未被接纳的订单均无当前预测。
- `actual`只在真实 `deliver` 完成事件出现后生成。模拟时间超过预计签收时刻本身不能创建实际记录。真实到达和服务来自后端事件，不是GPS观测。

暂停待规划、订单输入版本未追平、路况版本不符或尚无应用计划时，`timeline.stale=true`且旧 `expected`全部隐藏，并提供原因。实际签收历史继续保留。低余量筛选只作用于当前有效预测；未接纳原因仍应在拒单证据中查看。

### 无法接单的原因

`OrderExplanation`包含 `order_id`、原失败 `reason`、中文 `summary`、`scope='heuristic_candidate'`、代表性 `attempts`与待验证的 `suggestions`。

每个失败尝试具有 `hub`、`vehicle`、`stage`、`code`、`order_ids`、`load`、`capacity`、`service_end`、`deadline`、`source`、`target`。未适用或未取得证据的字段为null，不能编造数值补齐。容量字段始终由原始Decimal结果转为字符串，前端原样展示；不得转float求和、用epsilon放宽或用车队总容量替代单车容量。

诊断在已有候选评估与站点尝试中记录，不另写第二套可行性算法或事后猜测原因。每个失败站点保留代表性最终失败证据，不声称枚举了全部候选或所有道路。新增订单可能使已经承诺的另一订单超窗；证据中的阻塞订单ID指实际失败任务，不自动替换为新增单ID。

客户配送阶段明确记录签收完成时刻和截止；中转卸货阶段明确标为批次卸货约束，不能把卸货时间描述成客户签收时间。不可达说明定位候选连接及方向；当前主目标路径或插入尝试失败不等于全路网无可行解。

`explanations.source`区分 `applied_plan`、`blocked_proposal`与 `none`。自动续程无法安全应用时保存失败提案证据，但保留原有效计划、实际位置、货物和事件。只读 `prepare()`不替换这些证据。后续订单、路况或实际时刻变化后，旧解释标记 `stale`，只能作为上一次尝试的记录。

调整建议是下一步可检查项，不是保证成功的修复。容量等运营参数仍只能在未执行的新场景试算；调整窗口或参数后必须由原规划器及独立验证器重新确认，不能在展示层放宽约束。

## 文件职责与复杂度

| 文件 | 职责 |
|---|---|
| `src/logiroute/dispatch/models.py` | 新增不可变失败证据与逐单解释契约；Plan附加解释列表 |
| `src/logiroute/dispatch/algorithms/__init__.py` | 原候选评估可选输出失败证据，不改变评分、顺序或成功判定 |
| `src/logiroute/dispatch/algorithms/planning.py` | 保留站点尝试中的实际失败及阻塞任务 |
| `src/logiroute/dispatch/explanations.py` | 将结构化事实转换为说明与建议，不执行调度 |
| `src/logiroute/dispatch/insights.py` | 只读剩余行程比较、事件时间轴和证据有效性投影 |
| `src/logiroute/dispatch/session.py` | 成功应用时捕捉证据、维护最近尝试、同步快照 |
| `frontend/src/dispatch/components/PlanningInsights.tsx` | 摘要、拒单详情和逐单时间区间展示 |
| `frontend/src/dispatch/planning-insights.mjs` | 纯展示过滤、图轴定位、精确文本格式；不做配送决策 |

设A为计划动作及清单项总量、E为已完成事件及清单项总量、N为订单数、K为车辆数：影响摘要、时间轴及序列化分别为线性 `O(A+E+N+K)` 时间和相应线性空间。只保留最近一次影响摘要与最近失败／应用提案，不维护无限增长的路线版本历史。事件历史仍遵循原会话模型。

记录失败证据不新增最短路径求解或完整候选重演；仅在已经执行的失败检查处附加结构化记录。原算法阶数不变，失败记录涉及的订单ID与站点尝试另有线性存储成本。前端区间坐标与过滤为 `O(N)`，不用现成排序、图表库或算法库。

### 浏览器验收

通过真实界面新建严格Seed42场景、规划、搜索O12的时间轴。窗口9.78–15.78分，预计到达与服务开始约11.78分、签收约13.78分、余量2分，“实际签收”仍为未签收。

随后从界面新增 `DEMO_WINDOW`（P27、1kg、urgent、截止0.001分），查看三个中转站候选的拒单证据；再取消尚未装货的O1，后端自动重规划。道路距离及模拟成本未变，但剩余服务由24变23，O8、O10、O9、O2、O3、O16各预计提前约2分。这个案例保留了“几何不变但服务时刻改变”的事实。
