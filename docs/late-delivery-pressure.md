# 超时压力场景与签收优先级

Dashboard 的运营档案默认使用 `pressure` 时间窗；旧 `strict` 与 `relaxed` 显式入口继续采用所有订单的签收完成硬截止。压力场景在 `config/dispatch_bjut_operational.json` 中按优先级配置窗口范围和硬截止优先级。对每张原始订单独立、按固定 Seed 抽取截止，不用“两个目标都能按时送达”筛选结果。故初始化就可能有超时订单。时间单位是模拟分钟，路线仍使用真实有向边和同一手写 Dijkstra。

| 优先级 | 时间窗口径 | 规划和执行 |
| --- | --- | --- |
| 特急 `critical` | 签收完成必须不晚于截止 | 硬约束；插单预检失败则整笔回滚，提示延后截止。 |
| 紧急 `urgent` | 允许晚签收 | 先于普通订单接纳；在可行候选中先减少紧急迟到订单数和迟到分钟。 |
| 普通 `normal` | 允许晚签收 | 在紧急迟到相同的候选中再减少普通迟到订单数和迟到分钟。 |

可行插入比较在原主目标前加入 `(紧急迟到数, 紧急迟到分钟, 普通迟到数, 普通迟到分钟)`，同一新订单的可用中转站也比较整份候选续程的此四元组，最后才比较距离或成本。容量、方向、道路封闭、最早服务开始、实际返仓和特急硬截止仍必须满足。贪心没有全局最优保证；某个优先级的迟到减少是其实际比较过的候选之间的选择，不是对全部排列的证明。

独立计划验证器、执行器和历史审计各自检查同一完成截止口径。低优先级已超时仍可签收，并记录负余量；特急迟到仍判无效。`studio.planned_late_orders` 与 `studio.late_orders` 分别给预计和实际／当前逾期事实；模拟罚金按超时订单逐单计，在运营参数中与运输费用分列。已送达订单的实际签收时间由事件记录确定，不能仅看当前时钟。

旧严格窗口仍是“所有订单均须按时”的对照。用户切换时间窗模式时必须新建场景；已有在途会话不重写订单或车辆载荷。道路状态变化、插入或合法取消订单后的自动重规划仍只在已进入动作完成后的检查点应用独立验证通过的续程。
