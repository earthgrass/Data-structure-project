# 第二次检查：道路拥堵与车辆载重

课程题目要求有向加权道路、车辆载重限制，以及拥堵导致耗时增加20%以上时的重规划。本页对照当前可运行系统，不把模拟路况说成实时交通数据，也不把启发式规划说成全局最优。

## 代码与数据结构

| 要求 | 当前实现与检查入口 |
| --- | --- |
| 有向带权道路 | `core/edges.py` 的 `Edge` 保存源/目标、距离、时间、成本与交通状态。`graph/logistics_graph.py` 以邻接表保存有向边，按需导出邻接矩阵。反向道路是另一条独立边。 |
| 校园路网 | `data/bjut/campus-network.json` 提供离线道路与折线；`dispatch/real_map.py` 加载成图。默认校园场景为342个路由节点、768条有向边，2仓库、30个候选配送地点、5个设施中默认启用3个运营站。 |
| 拥堵权重 | `config/dispatch_v2.json` 的 clear/light/moderate/congested 分别乘以1/1.2/1.5/2；blocked 不可通行。`dispatch/traffic.py` 从原始边权重重建快照，时间增量进入模拟成本，不对已经拥堵的权重重复相乘。 |
| 重规划 | `dispatch/session.py` 记录交通版本并在动作检查点安全重规划；`api/routes/dispatch.py` 在手动路况变更时调用。已进入的道路动作按进入时的版本完成，后续路线采用新版本。`frontend/.../TaskPanels.tsx` 可以选择有向道路和拥堵等级，地图以不同线型显示拥堵/封路。 |
| 逐车载重 | `dispatch/models.py` 中 `VehicleSpec.capacity` 与 `Parcel.demand` 均为 Decimal。`dispatch/algorithms/planning.py` 和 `dispatch/algorithms/__init__.py` 在装货及候选路线检查单车容量；`dispatch/validation.py` 与 `dispatch/audit.py` 分别独立验证计划和实际历史。车队总容量不能代替单车容量。 |
| 参数试算 | `config/operations_studio.json` 设置干线150kg、末端50kg及模拟油耗/工时/维护费。Dashboard 的运营参数可逐车改容量；`dispatch/studio.py` 在独立会话重算道路成本和完整计划，原会话不被试算修改。 |

题目中的“耗时增加20%以上”已经涵盖：`light` 恰为20%，`moderate` 为50%，`congested` 为100%；Dashboard 的自动重规划对交通变更在检查点触发。另一个未启用自动重规划的运营入口仍有20%阈值判断。封路在两个目标下均排除，拥堵只改变时间及相应模拟成本，方向和距离不变。

## 可复现实例

在 `bjut-studio`、Seed 42、宽松时间窗、`cost` 目标的完整计划中，选取实际使用的有向边 `T_CENTER → R1808717170`，从畅通改为严重拥堵：该边耗时由 **0.1102878286672149** 增至 **0.2205756573344298** 分钟，交通版本变为1；自动重规划状态为 `applied`，计划独立验证有效，总距离从 **11.192667607587481** 变为 **11.195049695123341** km。车辆 CENTER 的剩余行驶时间增加约0.11028782866721443分钟；路线受硬约束与路径选择共同影响，不保证每次改路况都改变距离。

另取相同场景与订单，在隔离参数试算中把四辆车容量分别设为 **0.1kg**：原容量下接纳24/24单，受限容量下接纳0/24单，24单均列为未接纳；部分计划的独立验证仍为有效。原订单与时间窗保留，不能把0/24当成完整配送。

演示时在“交通与路线”选择上一份计划实际使用的有向道路，改为“严重拥堵”并应用；再看“路线变化”与“实验与审计”。载重演示在“运营参数”降低车辆容量、试算，再查看接纳数和拒单原因。道路权重、车辆容量、原计划与试算后的计划应分开截图说明。

## 尚未实现的扩展提示

题目“实现提示”举例提出每30秒随机修改10%道路、仅增量更新受影响路径段。当前演示是可控手动模拟道路状态，交通版本变更后重新运行现有手写 Dijkstra；没有定时随机交通源或增量最短路算法。第二次检查应按真实功能演示，不声称这两个提示已经完成。
