# 配送调度算法审查（2026-10-18）

> 历史审查记录：本文中的 NN / CFI + 2-opt 曾是默认流程，现已由
> [Dijkstra 距离矩阵 + 有向 TSP 搜索](algorithms-tsp.md) 替代。

## 结论

地图上的直线距离不等于有向道路的最短路；时间窗也可能要求绕序服务。
不过原默认规划器确实有可改进之处：只从可行插入（CFI）出发，
2-opt 又固定第一个客户，容易停在较差的局部路线。直接改成纯最近邻
也不可靠：它在一些场景胜过 CFI，在另一些场景明显更差。

现在默认流程是：

```text
同一场景与主目标
  ├─ CFI 构造 ─ 受约束 2-opt ─┐
  └─ NN 构造  ─ 受约束 2-opt ─┴─ 优先服务订单数，随后比较主目标
```

两条分支共用一次调度作用域内的 `PathProvider` 缓存。每条配送段仍由
Phase 2 Dijkstra 求有向最短路，未引入现成求解包。候选反转重建真实
道路段、时间表与容量检查，只有可行且主目标严格改善时才接受。

## 查到并修复的问题

1. 2-opt 枚举从 `i=1` 开始，首个客户无法参与反转。改为 `i=0`，
   仓库仍固定，首个客户可换位。
2. NN 原来用另一次 `travel_time` 最短路估算时间窗，但实际行驶的是
   `distance` 或 `cost` 最优路。改用选中道路段的
   `cross_metrics['travel_time']` 传播，并修正回仓时间。
3. 2-opt 按目的地节点找订单，同一节点有多笔订单时可能把它们错认成
   同一笔。现在反转时同步移动订单 ID，再按 ID 重建元数据。
4. 2-opt 重建 `RoutePlan` 时丢弃种子的 `unserved_orders` 注记，可能把
   未完成订单隐藏。现在保留注记；NN 分支被选中时按未送达订单补充原因。

## 可复核对比

以固定场景和随机 seed `0,1,2,3,4,5,42,100,2026` 为样本，分别运行
`distance` / `cost`，共 20 组。对比修改前后的默认调度器，20 组都
保持 20/20 送达；其中 9 组主目标改善、11 组持平，没有恶化。

| 场景与目标 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| 固定场景 distance | 39.77 | 37.45 | -5.8% |
| seed=3 distance | 1522.20 | 1410.15 | -7.4% |
| seed=3 cost | 3560.36 | 3086.78 | -13.3% |
| seed=4 cost | 3750.34 | 3450.88 | -8.0% |
| seed=100 cost | 4462.11 | 4198.34 | -5.9% |

样本规模为 20 个订单，修改后单次规划约 0.18–1.13 秒。速度快主要来自
问题规模和路径缓存，并不代表求得全局最优。该方法仍是启发式：
2-opt 只枚举连续段反转，不能穷尽所有排列；地图上相近的两个点也可能
因为有向道路、道路权重或时间窗而不相邻。若要判断一对具体配送点，
需要同时查看两段之间的道路最短路权重、时间窗和完整闭环的目标值。

`frontend/npm run build` 通过。
