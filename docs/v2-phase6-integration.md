基线 `09616a7`，分支 `feat/multivehicle-dynamic-orders`。保留旧接口及原728项测试。
新增协议 `logiroute.v2.phase6` 和 `/api/v2`，新订单只采用签收完成截止。

新实体的 priority 支持 critical/urgent/normal，旧枚举字符串和默认状态不变。

硬约束：客户 service_end <= deadline；每车精确 Decimal 容量；货物实际可用；
真实有向道路；仓库/中转站角色；装卸时间及返程。critical 只对同车同批、货物可用的
未开始任务施加先于低级任务的顺序要求。urgent 优先参与可行候选比较，不要求跨车全局服务时刻排序。
新到特急不撤销已完成/进行中的原子动作，也不突破已接受订单的窗口或凭空装货。

## 两级物流实体

- 客户订单 ID 终身唯一；到站不是 delivered。位置为 warehouse / vehicle / hub / delivered。
- 干线运输任务与客户配送任务独立编号并引用原始订单清单；不重复统计客户订单。
- trunk 以仓库为基地；delivery 以合法 TRANSFER 节点为基地，不能改节点类型伪装仓库。
- 中转库存按订单 ID 与 Decimal 数量保存；装载从真实来源扣除、卸货写入真实目的地。
- 客户分组采用固定 travel_time 道路闭包，确定性最近可行站点；两目标共用初始输入。
- 首版每站一配送车、一辆干线车来自 JSON；不拆单、不跨站转货、不隐含增加车或改容量。
- 一次静态批次每车一趟；动态剩余行程可以先完成已装货行程返基地，再接下一显式批次，
  不优化任意多趟补货，也不在道路途中装载。

## 交通和执行

距离保持原义；effective_time=base_time*JSON factor；effective_cost=base_cost+
cost_per_delay*(effective_time-base_time)。blocked 从所有指标的候选道路中排除，不以非法无限边权表示。
每次交通更新前进 traffic_version，重新创建路径快照/单次闭包。沿用原手写 Dijkstra。
执行最小单元为道路边、装货、卸货、客户服务。当前已进入的原子动作按进入时版本完成；
其他未来动作停在下一节点/操作边界后重新验证。不重置位置、已载货物和已送达历史。
无可行后续路线则显示受阻与原因，不沿已失效路线继续，也不伪造完成。

## 动态事务与覆盖口径

客户可随时提交；cancel/expiry 仅适用于尚未出仓且未装载的任务，终态不回收 ID。
新订单收到 queued 不代表已装载。既有已接受货物是 protected 集合，新草案必须覆盖它们。
可安全应用的计划必须独立核验全部计划动作、库存守恒、protected 覆盖和所有新/旧订单分区。
不可接纳的新单明确留在 deferred/unserved；complete_all 与 safe_to_apply 分开，不能把范围内成功冒充全部订单完成。
如果旧路线因封路失效且草案不安全，车辆在检查点等待；如果旧计划仍有效，普通重规划失败保留它。
提交校验 session revision + traffic_version + input fingerprint，所有 API 写操作串行，陈旧请求409。
前端只应用不小于当前 revision 的后端快照，不自行扣载/签收；显式操作后刷新和短轮询。
